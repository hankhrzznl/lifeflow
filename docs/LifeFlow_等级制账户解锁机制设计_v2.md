## 一、概念定位（沿用 v1.0，未变）

用户不是在管理 6 个格子，而是在**经营自己从 1 级到满级的成长**。每个等级 = 一个账户被点亮 + 一组功能被开启。四账户（体能→情感→思维→意志）就是等级主线的四个节点。

与能量档位的关系不变：档位是日内形态（今天状态差 → 轻载呈现），等级是长期轴（当前经营几个账户）；今日呈现 = 等级决定功能范围 × 档位决定轻载程度。

## 二、设计原则（七条）

**① 双因子重定义：连续性 × 深度。**
v1.0 的"使用率 × 达标率"在情绪这类"纯记录、无目标"账户上无法成立，才导致后续等级偷偷退化成单因子。v2.0 把第二因子从"达标率"泛化为"深度"——投入是否真实发生，逐账户操作化：

| 账户 | 连续性因子 C | 深度因子 D |
|---|---|---|
| 体能（睡眠） | 近 7 天记录天数 | 达标天数（isOnTime，实际入睡 ≤ 目标入睡） |
| 情感（记录） | 累计记录天数 | 觉察深度：带标签的记录次数 |
| 思维（专注） | 近 7 天专注天数 | 累计专注分钟数（时间本身就是深度） |
| 意志（目标） | TodayStep 累计推进天数 | 近期推进密度（防止 14 天突击后弃用） |

升级条件统一为 **C ∧ D**，每级都是真正的双因子。

**② 节奏原则。** 新用户到满级中位 8–12 周；单级中位停留 ≤3 周；前段（Lv1–3）快、后段慢；任何一级不得存在数学上不可达的条件（每个条件对应的入口与默认值必须存在）。

**③ 可呈现原则。** 每个条件必须能写成「还差 X [天/分钟/次/个]」，在等级页实时展示——这是"条件透明"的落地标准。

**④ 失败不降级。** 等级只增不减。状态单调持久化，进度实时推导（§9）。

**⑤ 可推导不存储。** 一切累计值、达标值从现有表计算（它们本来就在表里），不新建计数器——清 localStorage 不丢进度，天然支持未来多端。

**⑥ 老用户不爬塔。** 按**全历史**数据一次性定级，就高不就低（§6）。

**⑦ 透明与可跳过。** 升级条件全程透明；庆祝每级一次、可跳过；文案零禁用词（以 `src/lib/terms.ts` 的 BANNED_WORDS 全集为准：理想、失败、未完成、断签、掌控、AI）。

## 三、等级阶梯（规范表 · 唯一事实源）

```
Lv1 体能账户（新手 · 只做睡眠）
Lv2 情感账户（觉察开启）
Lv3 思维账户（专注开启）
Lv4 意志账户（目标开启 · 四账户主线完成）
Lv5 体能深化（生理全模块）
Lv6 生活工具（工具开启）
Lv7 完整版（全功能）
```

| 升级 | 解锁内容 | 连续性因子 C | 深度因子 D | 展示文案示例 | 中位节奏 |
|---|---|---|---|---|---|
| Lv1→2 | Lv2 解锁：情感账户 · 情绪记录 | 睡眠记录：近 7 天 ≥5 天 | 睡眠达标（isOnTime）：近 7 天 ≥5 天 | 「再 3 天按时入睡就点亮情感账户」 | 7–10 天 |
| Lv2→3 | Lv3 解锁：思维账户 · 专注 | 情绪记录：累计 ≥7 天 | 带标签记录：累计 ≥3 次 | 「再记 2 天情绪」 | 7–10 天 |
| Lv3→4 | Lv4 解锁：意志账户 · 完整目标功能（方向页 + TodayStep + 目标创建/详情） | 专注：近 7 天 ≥3 天 | 累计专注（已完成）≥60 分钟 | 「还差 25 分钟专注」 | 2–3 周 |
| Lv4→5 | Lv5 解锁：饮水 · 训练 · 饮食 · 久坐 · 习惯 | TodayStep 推进：累计 ≥14 天 | TodayStep 推进：近 7 天 ≥4 天 | 「再推进 5 天」 | 2–3 周 |
| Lv5→6 | Lv6 解锁：备忘 · 倒数日 · 提醒 | 任一生理模块（饮水/训练/饮食/久坐/习惯）：累计使用 ≥7 天 | 有使用记录的模块 ≥2 个 | 「饮水再记 3 天，另试试训练」 | 1–2 周 |
| Lv6→7 | Lv7 解锁：陪练完整版 · 记账 · 吃药 · 功法养生 · 设置全功能 | 已解锁模块中 ≥3 个，各自累计使用 ≥7 天 | **二选一**：累计专注 ≥7 小时 ∨ TodayStep 累计推进 ≥30 天 | 「再养熟 1 个模块 + 专注还差 2 小时」 | 2–3 周 |

**口径说明**（全部可由现有表推导，见 §7）：睡眠记录天 = sleepLogs 去重日期；情绪记录天 = 两张 moodLogs 表日期并集；专注 = type='focus' ∧ completed=true，duration 按分钟计；TodayStep 推进天 = goalV2DailyActions 中 isCompleted=true 的去重 date 数。

**设计理由（相对 v1.0 的关键变化）**：

- **7 小时的迁移**：用户的"小时级门槛"想法是对的——它衡量真实投入而非打卡。但放在 Lv3→4 会让核心价值（目标）被锁 12–17 周。v2.0 把它移到 Lv6→7 作为深度因子：此时用户已使用约 2 个月，单次专注时长自然变长（25 分钟/天 → 7 小时约 17 天），门槛成立且不构成悬崖。
- **Lv3→4 的 60 分钟**：保留"小时级投入"性质（12 次默认 5 分钟即达），配合"近 7 天 3 天"确保是近期习惯而非一次性尝鲜。
- **Lv4→5 加"近 7 天 ≥4 天"**：防止 14 天集中突击后弃用——升级要求"最近还在推进"，这正是 v1.0"条件延续"想法的正确表述。
- **Lv5→6 的广度因子（≥2 个模块）**：体能深化的意义是"多点经营"，单模块 7 天 + 广度信号比模糊的"整体使用"精确且可呈现。
- **Lv6→7 深度二选一**：尊重不同用户的主线（思维型走专注、意志型走目标），同时保留 7 小时想法。代价是展示稍复杂，实现时"二选一"按较近的一项呈现。
- **Lv1 可排日程保留**（沿用 v1.0）：日程是工具性基建，不算第二件"经营事项"，不与①一次一事冲突。

**待决项（记录在案，不在 v2.0 解决）**：记账/吃药/倒数日/备忘等实用功能的强顺序解锁，是否改为"主线到达后分支自选"。v2.0 维持用户"等级解锁一切"的拍板设定；若上线后 Lv6→7 出现明显选择性流失（只想记账的用户卡在专注），再做分支化（§10 度量可直接暴露此问题）。

## 四、节奏模型

| 里程碑 | 最快 | 中位 | 说明 |
|---|---|---|---|
| Lv2（情绪可用） | 第 5 天 | 第 7–10 天 | 睡眠 5/7 双因子 |
| Lv3（专注可用） | 第 12 天 | 第 2–3 周 | 情绪 7 天 + 3 次标签 |

| Lv7（全功能） | 第 9 周 | 第 10–12 周 | 3 模块养熟 + 7 小时/30 天 |

## 五、关键规则（在 v1.0 六句话防护上修订）

| 规则 | 说明 |
|---|---|
| 失败不降级 | 等级只增不减；条件掉出只是"暂缓升级"，已解锁功能永不收回 |
| 老用户不重新爬塔 | 全历史一次性定级（§6），归来不回落 |
| 解锁时刻 = 庆祝 | 全屏轻庆祝 + 教练句（如「情感账户已开启。情绪记录今天可用。」）；**每级仅一次，可跳过**（尊重不想被游戏化的用户） |
| 未解锁功能 = 灰态可见 | 成长路径可见、不可用（「Lv4 开启 · 目标功能」）——动机可视化 |
| 低能量日不影响等级 | 档位是日内形态；等级只看长期使用与深度 |
| 升级条件对用户透明 | 等级页展示完整路径 + 「下一级还差什么」实时数值 |
| 禁用词防护 | 文案以 terms.ts BANNED_WORDS 全集为准（理想/失败/未完成/断签/掌控/AI）；未解锁一律正向表述「LvX 开启」 |

## 六、老用户定级与迁移

**定级算法（一次性）**：对 §3 每个升级条件，把其中的"近 7 天"替换为"**任意历史滚动 7 天窗口**"，用全历史数据计算可达到的最高等级，一次定级、落定不回算。这保证：中断归来的老用户不吃亏（修 v1.0 缺陷 #6），且历史认真用过的行为全部被承认。

**旧等级迁移**：现有 `lf-unlock-level`（CellId 版）的等级值予以尊重：最终定级 = max(数据定级, min(旧等级值, 7))。实现时需先确认旧版等级的取值范围再映射。

**定级后**：写入 reachedAt 时间戳；仅对定级过程中"新跨越"的等级触发一次庆祝（可跳过）。

## 七、边界情况与前置依赖（代码核查结果）

1. **睡眠目标双源（前置任务，P0）**：睡眠页当前用页面级 localStorage（默认 23:00），而 SleepGoalV2 表默认 23:30，两处未对齐（源码有 TODO）。等级判定直接读 `sleepLogs.isOnTime`（写入时已按当时目标算好），风险可控；但重做时应统一目标源为单一事实源，否则达标率口径长期漂移。
2. **onboarding 不设睡眠目标（前置任务）**：现状 onboarding 不写睡眠设置，新用户依赖默认值。《推倒重做方案_v2》Phase 4 的 onboarding（3 步）应含"推荐入睡时间"一步（默认 23:00 可改）；在此之前，判定按默认值进行，Lv1→2 依然可达（修"数学不可达"风险）。
3. **情绪双表口径**：连续性 = `healthDB.moodLogs.date ∪ lifeDB.moodLogs.date` 的去重天数；深度（带标签记录）两表并集计数（两表均有 tags 字段）。数据不丢铁律之下，两张表都算。
4. **专注口径**：`focusSessions` 仅计 `type='focus' ∧ completed=true`；duration 单位为分钟；未完成的会话不计入深度因子。
5. **TodayStep 去重**：`goalV2DailyActions` 的 date 索引非唯一，代码侧必须按 `isCompleted=true` 的 distinct(date) 计数。
6. **日期边界**：一律按本地自然日（各表 date 已是 YYYY-MM-DD 本地日期），不做时区换算。
7. **清空 localStorage**：等级可由 §6 定级算法从表中完整重建（等级本身可推导），只丢庆祝标记——无害，重新庆祝一次也无妨。
8. **Lv7 满级态**：见 §8。

## 九、数据与实现（零 schema 变更）

**架构原则：单调的存，可推导的算。**

- **持久化**（`localStorage: lf-unlock-v2`，仅单调标记）：
  `{ level, reachedAt: {lv: iso}, celebrated: {lv: iso}, migratedFromV1: boolean }`
- **推导**（每次判定实时计算，不落盘）：所有累计天数/分钟数/达标天数，直接查表——情绪并集、专注完成分钟、TodayStep 去重天、睡眠 isOnTime（§7 口径）。
- **判定**：纯函数，可单测：

```ts
type AccountId = 'physical' | 'emotional' | 'cognitive' | 'volitional';

interface UnlockState {
  level: 1 | 2 | 3 | 4 | 5 | 6 | 7;
  unlockedAccounts: AccountId[];
  unlockedFeatures: FeatureId[];
  next: null | {
    toLevel: number;
    requirements: Array<{
      label: string;          // 「还差 25 分钟专注」
      current: number; target: number;
      unit: 'day' | 'min' | 'times' | 'module';
      satisfied: boolean;
    }>;
  };
  maxed: boolean;             // Lv7 → true，切换安稳视图
}

// 升级检查时机：每天首次打开今天页（与能量判定同批，沿用 v1.0）
// 定级函数：placeFromHistory(allTables) → level（§6 算法，老用户/清缓存时调用）
```

- **升级逻辑**：每天判定一次"当前 level+1 的 C ∧ D 是否满足"→ 满足则 level+1、写 reachedAt、触发庆祝；不满足不动。等级值本身单调持久化，任何回退不可能发生。
- **迁移**：首启读旧 `lf-unlock-level`，按 §6 规则合并后写 `migratedFromV1=true`。
- **阈值配置化**：§3 所有数值集中在一个 `LEVEL_REQUIREMENTS` 常量对象，调参不改逻辑（§4 调参政策的落点）。
- **单测要求**：定级算法表驱动测试——新用户 / 30 天活跃老用户 / 中断 60 天归来老用户 / 清空 localStorage 后重建，四种用例定级结果符合 §6。

## 十、度量与校准

- **本地度量**：`reachedAt` 时间戳天然构成 days-to-level（首启日期可由最早一条记录日期近似）。隐私优先：只存本地，不上传。
- **验收期采集**：上线后 4 周，人工收集 ≥10 名种子用户的定级/升级时间线。
- **校准红线**：任何一级 30 天通过率 <40%，或中位停留 >30 天 → 调阈值（§4）；Lv6→7 出现"只想要某工具"的流失 → 评估待决项（分支化）。

- 清空 localStorage 后，等级从数据完整重建，不回落
- 庆祝每级仅一次、存在跳过入口
- Lv7 满级后呈现安稳视图，无新成长轴
- 上线 4 周节奏数据符合 §4 红线（否则调参）
